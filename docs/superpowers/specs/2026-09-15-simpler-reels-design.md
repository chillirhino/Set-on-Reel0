# Настройка рила: стеки, группы, мастер-рил

Дата: 2026-09-15

Вкладка «Ленты» переходит с ручной раскладки стеков на модель «количество плюс
шансы на длину». Плюс тумблер «low как прослойка».

## Что было и почему это сложно

На каждый символ задавалась сетка «сколько стеков длиной 1 / 2 / 3 / 4», кнопка
«+ длинный» для длин выше поля и флаг ∞. Длина ленты получалась как сумма
`длина × количество`.

Сложность не в числе полей, а в том, что пользователь держал в голове
арифметику: чтобы получить 28 символов, надо было самому подобрать `2×7 + 3×2 +
4×2`. Любая правка состава требовала пересчёта раскладки.

## Что стало

Символ на риле описан тремя вещами:

1. **сколько всего** — одно число;
2. **шансы на длину стека** — по колонке на длину 1..6 (или до высоты поля, если
   она больше), плюс «+ длиннее» для редких случаев;
3. **∞** — разрешена ли склейка своих стеков.

Правило разрешения конфликта: **количество это закон, шансы это ориентир.**
Длины тянутся по шансам, пока не наберётся заказанное количество, последний стек
подрезается по остатку. Ни одной длины не задано — символ ляжет по одному.

Шансы относительные: 50/30/20 значит то же, что 5/3/2. Процент считает и
показывает интерфейс, пересчитывать соседей вручную не надо — та же схема, что у
весов скрытых символов.

Это ровно `StackRule(symbol_id, count, sizes)` из `rules.py`: модель, на которой
уже работает половина инструмента с импортом `.py`-игры. Расходиться двум
половинам было незачем.

## Хранение

```json
"reels": [
  { "3": { "count": 21, "sizes": { "1": 50, "2": 30, "3": 20 }, "infinity": false } }
],
"filler_low": false
```

Вместо `{ "stacks": [[1,5],[2,3],[4,1]], "infinity": false }`.

## Одна сборка стеков на две половины

`generate.py::assemble_sizes` уже умел тянуть длины по шансам. Реализация
переехала в `strips.py::assemble_sizes(count, sizes, rng)`, а в `generate.py`
осталась однострочная передача со старой сигнатурой — её тесты не пришлось
трогать, и правило «количество — закон» теперь одно на весь инструмент.

Длины тянутся заново на каждой из 200 попыток укладки: набор стеков, который не
разводится по правилам пересечения, может сойтись при другом наборе.

## Прослойка

Тумблер один на весь сет — чередование дешёвого и ценного это стиль игры, а не
свойство отдельного барабана.

**Локальное предпочтение не работает.** Первая версия делала так: после
low-стека выбирать не-low и наоборот. Как только ценные кандидаты кончались,
весь остаток low валился в хвост одной кучей — то есть ровно то, от чего
прослойка должна избавлять. На проверочной ленте самая длинная полоса одного
класса осталась 10 из 40.

**Работает распределение по промежуткам.** Не-low раскладываются каркасом, low
делятся по промежуткам между ними поровну, остаток от деления достаётся
случайным промежуткам — иначе лента выглядит линованной. На той же ленте самая
длинная полоса одного класса упала с 10 до 3, а картина читается как
`██··███··██···█··██··███··██···███··██··`.

Прослойка меняет только порядок, не состав, поэтому RTP линий она не двигает.

Обещание честное настолько, насколько позволяет арифметика: если low-стеков
меньше, чем промежутков, часть ценных всё равно встанет рядом.

## Перенос существующих сетов

`count` = сумма `длина × количество` — та же арифметика, что давала длину ленты
раньше, поэтому **состав переносится точно**. `sizes` = сегодняшняя раскладка
длин, переведённая в проценты; так же `service.default_rules` восстанавливает
правила из готовых лент.

Проверено на рабочем сете `zeus power 2`: количества совпали по всем пяти рилам
до символа.

## Что теряется

**Точность раскладки.** Раньше выходило ровно 3 стека по 2 и один по 4. Теперь
в среднем столько же, но каждый раз заново. Следствия:

- **RTP по линиям не меняется.** Он зависит только от количеств символов на
  барабане, а не от порядка и не от раскладки стеков. Количества сохраняются
  точно.
- **Частота скаттера и бонуса гуляет** от генерации к генерации: они смотрят в
  окно из 4 рядов и видят именно раскладку.
- **Старый конфиг в файле не сохраняется.** Первая же правка сета перезаписывает
  `stacks` на `count` + `sizes`, и вернуть точную раскладку будет нельзя. Сами
  ленты при этом целы — они лежат в `strips` и `strips.txt`, — приблизительным
  становится только рецепт. Кому важен старый рецепт: «Экспорт файлом» до первой
  правки.

Это цена упрощения, и она там, где её и заказывали: числа уходят, точность
вместе с ними.

## Группы символов

Группа — пульт «поставь всем одинаково». Выставил количество и шансы на строке
группы — они разошлись по всем её символам.

### Группа не хранит значения

Раз значение копируется в каждый символ, группе не нужно своё место для чисел:

```json
"groups": [ { "name": "роялсы", "members": [1, 2, 3, 4] } ]
```

Следствия, ради которых модель и выбрана так: `reels` остаётся обычным, генерация
о группах не знает ни строки, переносить существующие сеты не нужно, а разбор
группы ничего не теряет — символы остаются со своими значениями и просто
перестают быть связанными.

### Решения

- **Количество копируется, а не делится.** 30 на группу из четырёх роялсов — это
  120 символов в ленте. Группа отвечает на «поставь всем по 30», а не на
  «роялсы занимают 30 позиций».
- **Членство общее на сет, значения по рилам.** Группа собирается один раз и
  видна на всех рилах, но количество и шансы у каждого рила свои: крайние
  барабаны обычно настраивают иначе середины.
- **Символ состоит максимум в одной группе.** Иначе «применить ко всем» теряет
  однозначный смысл. При входе в новую группу символ выбывает из прежней.
- **Поля членов заморожены.** Они показывают унаследованное и не редактируются:
  глядя на строку, всегда ясно, кто её задаёт. Нужно отличающееся — вынь символ
  из группы.
- **∞ тоже в группе.** Раз поля членов заморожены, флаг склейки пришлось бы
  заморозить вместе с ними, поэтому группа управляет тремя вещами: количество,
  шансы, ∞.

### Разошедшиеся значения

Единственный способ получить разные значения у членов — собрать группу из
символов, которые уже отличались. Тогда строка группы показывает **«разные»**, и
первая правка сводит всех к значению первого члена. Молча при сборке ничего не
перетирается.

### Интерфейс

Строка группы — та же форма, что у одиночного символа: те же шкалы, то же поле
«сколько», та же ∞. Отличается акцентной рамкой и тем, что слева стоит имя
группы, а не символ. Члены идут под ней с отступом и приглушённые.

Левая часть строки держит ровно 188 пикселей у всех трёх видов строк — шапки,
группы и вложенного члена. Иначе колонки шансов поехали бы относительно своих
чисел в шапке, а это та самая проблема, которую выравнивание и решало.

Символ берётся **за миниатюру** и бросается на строку группы: тянуть строку
целиком при её высоте неудобно. Вынуть — крестиком на строке члена или броском в
зону «вне групп».

### Что тронуто по краям

- удаление символа выводит его из группы, иначе в файле остался бы мёртвый id;
- смена и обмен id переносят членство вместе с номером — там же, где уже
  переезжают стеки, правила пересечения, ленты и веса скрытых;
- «На все рилы» и «Очистить рил» не менялись: они про значения, а членство от
  рила не зависит.

## Мастер-рил и паттерн

Вместо настройки пяти рилов по отдельности настраивается один эталон —
**мастер-рил**, — а пять выводятся из него множителями **паттерна**.

### Ползунок это множитель

Середина шкалы — **×1 всегда**, при любом потолке. Нижняя половина растягивается
на диапазон 0…1, верхняя на 1…макс. При потолке ×3 и мастер-количестве 30:

| ползунок | 0 | 25% | 50% | 75% | 100% |
|---|---:|---:|---:|---:|---:|
| множитель | ×0 | ×0.5 | **×1** | ×2 | ×3 |
| символов | нет | 15 | 30 | 60 | 90 |

Ноль убирает символ с этого рила совсем. Потолок задаётся **на каждую цель свой**:
скаттеру нужен ×2, чтобы тонко разводить рилы, а лоу может понадобиться ×10 —
один потолок на всех сделал бы половину ползунков бесполезно тупыми.

Хранится **множитель, а не положение ползунка**. Поэтому правка потолка ×3 → ×5
не двигает уже выставленные количества, а только растягивает шкалу под
ползунком.

### Паттерн меняет только количество

Шансы на длину стека и ∞ берутся из мастера как есть, одинаково на все пять
рилов. Ползунок значит ровно «×N от мастер-количества» и ничего больше: один
регулятор, делающий две разные вещи, читался бы вдвое хуже.

### Пять рилов не перезаписываются

Ключевое решение. Конфиги выводятся **на ходу** в момент генерации:

```python
def effective_reels(doc):
    if not doc["master_on"]:
        return doc["reels"]
    ...  # мастер × множители, никуда не записывается
```

Если бы Generate писал результат в `reels`, ручная настройка пяти рилов стёрлась
бы при первой же генерации, и тумблер режима стал бы ловушкой. А так `reels`
лежит нетронутым, и выключение режима возвращает его целиком.

### Цель паттерна

Цель это `id:N` или `group:имя` — та же запись, что у правил пересечения. Целями
служат группы и одиночные символы, ровно как строки в таблице рила: **у члена
группы своей цели нет**, иначе один символ тянули бы две настройки сразу и было
бы непонятно, какая сильнее.

### Хранение

```json
"master": { "3": { "count": 21, "sizes": {…}, "infinity": false } },
"master_on": false,
"pattern": { "id:11": { "max": 3, "mult": [1, 1, 0, 1, 2.4] } }
```

Отсутствие записи в паттерне означает ×1 на всех рилах — по умолчанию паттерн не
меняет ничего.

### Интерфейс

Тумблер «Мастер-рил» в панели вкладки «Ленты». При включении переключатель рилов
исчезает — правится один эталон, — а мастер засеивается из текущего рила, если
ещё пуст. Существующий мастер при этом не перетирается.

Паттерн — **своя вкладка**, сразу за «Лентами»: слева выбранная цель и её
потолок, дальше борда из колонок по числу рилов.

Вкладка видна всегда, даже когда режим мастера выключен. Прятать её было бы
хуже: вкладки прыгали бы от состояния сета, и найти паттерн можно было бы только
случайно. Вместо этого страница объясняет, что множить пока нечего, и предлагает
кнопку «Включить мастер-рил» прямо там. В колонке — клетки барабана, множитель с
получающимся количеством и вертикальный ползунок с отметкой ×1 посередине. Снизу
список целей: группы и одиночные символы, у тронутых стоит метка «≠».

Пока ползунок тянут, на сервер не ходим: цифры пересчитываются на месте, запись
уходит по отпусканию. Замерено — четыре шага перетаскивания дают ноль запросов,
отпускание один.

**Символа нет в мастере — панель говорит об этом вслух.** Множитель умножал бы
ноль, ползунки крутились бы, а лента не менялась; такое молчание было бы худшим
видом поломки.

## Тесты

- сумма длин всегда равна заказанному количеству, при любых шансах;
- последний стек подрезается по остатку;
- длины с нулевым шансом не тянутся;
- относительные шансы: 50/50 и 1/1 дают одно и то же;
- без заданных длин символ ложится по одному;
- длина ленты равна сумме количеств, состав точен, один сид даёт одну ленту;
- прослойка разбивает длинные полосы одного класса и не даёт low скопиться
  в хвосте;
- прослойка не меняет состав;
- невозможное соотношение (low вдесятеро больше) не ломает генерацию;
- перенос: количество совпадает со старой арифметикой, длины становятся шансами,
  новый вид конфига переносом не затрагивается, перенесённый сет генерирует
  заказанную длину.

Группы:

- одно значение доходит до каждого члена, включая ∞;
- количество копируется, а не делится: 30 на четырёх даёт 120 в ленте;
- значения у рилов независимы при общем членстве;
- символ выбывает из прежней группы при входе в новую;
- пустую группу настроить нельзя, повторное имя и переименование на занятое
  отбиваются;
- разбор группы сохраняет значения символов;
- удаление символа и смена его id тянут членство за собой;
- мёртвые id выбрасываются при чтении, сет без ключа `groups` открывается чисто.

Мастер-рил и паттерн:

- без паттерна пять рилов равны мастеру символ в символ;
- ×1 не меняет ничего при любом потолке, ×0 убирает символ с рила;
- множитель обрезается потолком, понижение потолка подрезает выставленные;
- шансы и ∞ едут из мастера нетронутыми;
- множитель на группу двигает всех её членов, у члена своей цели нет;
- переименование группы тянет её паттерн, разбор — удаляет;
- **ручные пять рилов переживают генерацию в режиме мастера**, и выключение
  режима их возвращает;
- включение режима сеет мастер из указанного рила и не перетирает уже
  существующий;
- сгенерированные ленты следуют паттерну по составу;
- смена и удаление id тянут за собой и мастер, и паттерн;
- сет без ключей `master` / `pattern` открывается чисто;
- кривой payload даёт внятную ошибку, а не пятисотку.

# Поправка от 2026-09-16: обратно к числу стеков

## Что оказалось не так

Модель «количество символов плюс шансы на длину», описанная выше, порождала
**одиночные символы в лентах**. Причина в правиле «количество — закон»: длины
тянулись по шансам, а последний стек подрезался по остатку. Когда до конца
оставался один символ, он и становился стеком длины 1 — при разрешённых длинах
2 и 3.

Замерено: **43% сборок** содержали одиночку, и это не зависело от заказанного
количества. Остаток случайный, поэтому 26, 30 и 41 символ вели себя одинаково.

```
длины 2 и 3, количество 30 → [2,2,2,2,2,2,2,2,2,2,2,2,2,2,1]
                                                           ^
```

## Что стало

Символ на риле описан **числом стеков каждой длины**. Разброс 6 / 2 / 2 по
длинам 2 / 3 / 4 значит шесть двоек, две тройки и две четвёрки: десять стеков и
6×2 + 2×3 + 2×4 = 26 символов.

Разброс — это и есть стеки, а не пропорции: что вписал, то и ляжет. Никакого
округления нет вообще. Количество символов и число стеков считаются из этого и
показываются, но не вводятся: два места для одного значения неминуемо разошлись
бы.

**Стек неделим, поэтому остатка не возникает, а длина 1 попадает в ленту только
если её заказали.** Это свойство конструкции, а не проверка, которую можно
обойти.

Заодно из сборки ушла случайность: тот же заказ даёт тот же набор стеков всегда.
Генератор по-прежнему ищет порядок, но состав больше не гуляет.

## Множитель паттерна масштабирует стеки

Раньше он умножал количество символов. Теперь умножает **число стеков** каждой
длины, а символы считаются из них: иначе множитель снова порождал бы остаток.

Следствие, которое стоит знать: половина от 9×2 + 4×3 это 5×2 + 2×3 = 16
символов, а не «половина от 30». Девять стеков пополам — это 4.5, и половина
идёт вверх.

Попутно исправлено округление: `round()` в Python округляет 4.5 к чётному, то
есть к 4. Для множителя это сюрприз, поэтому половина всегда идёт вверх.

## Перенос

Открываются обе прежние формы:

- список пар `[[длина, стеков], …]` — это уже прямо число стеков;
- пара «количество символов + шансы» — подбирается целое число стеков по каждой
  длине так, чтобы сумма символов была как можно ближе к заказанной, а форма
  разброса — к прежним шансам.

Проверено на рабочем сете `zeus power 2`: **худшее расхождение по составу — один
символ** на тринадцати символах. RTP линий зависит только от количеств, поэтому
он сдвинулся минимально. После переноса незаказанных одиночек в лентах не
осталось ни одной.

## Что осталось от прежней модели

`strips.assemble_sizes` никуда не делся: по нему работает контур с импортом
`.py`-игры, где `rules.StackRule` описан именно количеством и шансами. Две
модели больше не делят одну реализацию, потому что у них разный смысл заказа, —
и этот же дефект с подрезкой там остаётся. Контур сетов его не касается.


## Состав рилов и генерация на вкладке «Паттерн»

### График состава

Справа от ползунков — столбец на каждый рил, поделённый на доли целей. Столбец
всегда полной высоты: сравниваются **доли**, а не длины лент, а абсолютные числа
стоят подписью снизу. Наведение на полосу даёт имя, количество символов и
процент; клик выбирает эту цель в ползунках слева.

Оттенок внутри одного типа чуть разный — два спешела подряд иначе слились бы в
одну полосу.

**Считает сервер, а не интерфейс.** `sets.state()` отдаёт поле `derived` — вывод
`effective_reels`, то есть ровно то, что пойдёт в генерацию. Считать состав на
фронтенде значило бы держать вторую реализацию тех же правил, и она рано или
поздно разошлась бы с настоящей.

### Generate Reels прямо тут

Кнопки «Generate Reels» и «↺ Новые сиды всем» продублированы на вкладке, а ленты
рисуются в тот же вид, что и на «Лентах». Обработчики вешаются на элементы, а не
на id, поэтому обе копии живые — клонировать DOM было бы нельзя.

Отдельной работы под «эти ленты крутит симуляция» не потребовалось: так было
всегда. Генерация берёт конфиги из `effective_reels`, кладёт результат в
`strips`, а «Статистика» крутит то, что там лежит.

### Предупреждение о разошедшихся настройках

График показывает, что выйдет **сейчас**, а ленты лежат с прошлой генерации.
Расхождение нашлось сразу при первой же проверке: состав говорил 465 символов на
риле 1, а лента была на 340.

Молчать об этом нельзя — симуляция крутит ленты, а не настройки, поэтому цифры
на «Статистике» относились бы к прежнему паттерну. Теперь при расхождении длин
обе вкладки пишут красным, какие рилы пересобрать, и предупреждение гаснет само
после генерации.


### Generate выглядел сломанным, потому что молчал

Кнопка «Generate Reels» работала: запрос уходил, ленты пересобирались. Но
генерация детерминирована — **тот же сид даёт ту же ленту**, — поэтому при
неизменных сидах результат получался побайтово прежним: ни длины, ни сиды, ни
текст не менялись. Со стороны это неотличимо от мёртвой кнопки.

Теперь генерация отчитывается всегда, и отдельно — когда ничего не изменилось:

> ленты те же: сиды не менялись, а при том же сиде раскладка повторяется —
> нажми «↺ Новые сиды всем» (465 · 329 · 217 · 338 · 267)

Молчание в ответ на действие — худший вид обратной связи: пользователь не может
отличить «сделано» от «сломано».

### Ленты текстом на обеих вкладках

Блок с плоским выводом (`8 8 8 8 2 2 2 2 9 9 30 30 …`, по строке на рил) и
кнопкой «Скопировать» продублирован на вкладку «Паттерн». Тот же текст, что
пишется в `sets/<сет>/strips.txt`.

### Проверено, что симуляция крутит именно эти ленты

Не утверждением, а сверкой: состав, показанный на «Статистике», сложен из тех же
1616 символов, что лежат в текстовом выводе — символ в символ по всем id.


## Приоритет длин стека по рилам

Общий множитель паттерна масштабирует все длины разом. Приоритет длин добавляет
второй множитель — на конкретную длину конкретного рила:

```json
"pattern": {
  "id:9": {
    "max": 3,
    "mult": [1, 1, 1, 1, 1],
    "lengths": { "2": [2, 1.5, 1, 0.5, 0], "4": [0, 0.5, 1, 1.5, 2] }
  }
}
```

Они перемножаются: общий отвечает на «сколько всего стеков», этот — на «каких
именно». Запись с единицами на всех рилах не хранится: ×1 везде и значит «как в
мастере».

Выбрана полная таблица «длина × рил», а не один ползунок перекоса, потому что
перекос выражает только градиент коротких-к-длинным, а таблица — любую раскладку,
включая «больше двоек И четвёрок, меньше троек».

Строк в таблице столько, сколько длин реально задано у цели в мастере: у вайлда с
двойками и четвёрками это две строки по пять клеток, а не шесть строк.

Проверено сквозным прогоном: при раскладке 2.0/1.5/1.0/0.5/0 для двоек и
0/0.5/1.0/1.5/2.0 для четвёрок в сгенерированных лентах на первом риле остаются
только двойки, на пятом только четвёрки.

## Папка картриджа на диске

Браузер открывает папку через File System Access API и читает-пишет в ней файлы
напрямую. Формат папки — тот же `set.json` рядом с `images/`, поэтому нынешние
сеты открываются без конвертации.

**Хранилище переписывать не пришлось.** Нужные операции уже были:
`/api/sets/export` отдаёт сет одним объектом с картинками в base64,
`/api/sets/import` разворачивает такой объект обратно. Открытие папки — это
чтение файлов и вызов import, сохранение — вызов export и запись файлов.

Сервер остаётся оболочкой: считает и симулирует, а долговечная копия лежит у
пользователя. Handle папки живёт в памяти вкладки, поэтому повторное сохранение
идёт без диалога.

Работает в Chrome и Edge; где `showDirectoryPicker` нет, кнопки не показываются.

### Широкий catch съел настоящую ошибку

Первая версия чтения папки оборачивала весь блок с картинками в один
`try/catch` с комментарием «папки images может не быть». При проверке картинки не
доехали, и ошибка утонула молча — отладка ушла в сервер, хотя причина была в
чтении файлов.

Теперь ловится только отсутствие папки, а сбой чтения отдельного файла
доходит до пользователя.
