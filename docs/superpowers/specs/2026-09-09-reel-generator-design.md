# Reel Generator — дизайн

Дата: 2026-09-09
Статус: утверждён пользователем, готов к планированию реализации

## Задача

Инструмент, который генерирует ленты (reel strips) слота по заданным условиям — состав,
стеки, дистанции между символами — и сразу показывает, что получилось: раскладку
картинками, состав по каждому рилу и точный RTP.

Проект самостоятельный, с нуля, в `/Users/mark/2_Claude/Reel Generator`. Соседний
`reelsviewer` не трогаем и не тянем как зависимость.

## Что делает первая версия

1. Импортирует конфиг игры из `.py`-файла привычного формата.
2. Подгружает картинки символов из указанной папки и маппит на id.
3. Даёт задать правила на каждый рил каждого рилсета: кол-ва, стеки, дистанции.
4. По кнопке генерирует ленты.
5. Показывает раскладку картинками, таблицу состава и точный RTP.
6. Экспортирует ленты обратно в `.py`-формат игры.

Чего в первой версии нет: автоподбора кол-в под целевой RTP, расчёта RTP фриспинов и
бонуса, правил на окно экрана («не более 2 special в окне из 4 рядов»).

## Формат игры

### Символы

```python
symbol_09 = 'wild', {3: 15, 4: 70, 5: 300}, 'el_wild'
symbol_10 = 'scat', {3: {'tb': 2, "fs": 8},}, 'el_scatter'
symbol_11 = 'bonus', {}, 'el_bonus'
symbol_12 = 'hide', {}, 'hidden'
```

Разбирается в: `id` (из имени), `kind` ∈ {line, wild, scat, bonus, hide}, `pays`
(словарь длина → выплата; у скаттера значение — вложенный словарь с `tb` и `fs`),
`asset` (имя ассета в игре, не путь к картинке).

### Линии

```python
payline_01 = [0, 0, 0, 0, 0]
```

20 линий, 5 рилов, ряды 0–3. Отсюда окно экрана — 5×4.

### Рилсеты

```python
reels_spins_1 = '''
9 9 1 1 2 2 ...
...
'''
```

Одна строка = один рил, 5 строк = рилсет. В файле несколько рилсетов
(`reels_spins_1..4`, `reels_freespins_0..1`). Порядок рилсетов и их имена сохраняем
при экспорте.

### Экспорт

Обратно в тот же вид: `reels_<имя> = '''…'''`, символы через пробел, по строке на рил.
Игровой `.py` перезаписывается только по явной команде «экспорт»; остальные объявления
в файле сохраняются как есть.

## Картинки

Указывается папка (по умолчанию `/Users/mark/2_Claude/symbols`). Авто-маппинг: первое
число в имени файла = id символа. `sym5.png → 5`, `sym11_1.png → 11`, `sym12.png → 12`.
Если на один id несколько файлов — берётся первый по алфавиту, остальные доступны в
выпадающем списке. Ручное переназначение любого файла на любой id сохраняется в проект.
Id без картинки рисуется плашкой с номером — генерация от этого не ломается.

## Классы качества

Каждому id ставится класс: `low` / `middle` / `high` / `special`. Классы используются
только правилами дистанции.

Дефолт при первом импорте: id 1–4 → low, 5–6 → middle, 7–8 → high, 9/10/11/12 → special.
Дефолт редактируется и сохраняется в проект.

## Правила

Правила задаются на каждый рил каждого рилсета. Есть кнопки «скопировать правила этого
рила на все рилы рилсета» и «на все рилсеты».

### Состав

Точное количество для каждого id. Длина ленты = сумма количеств, UI показывает её
онлайн. Id с количеством 0 на ленту не попадает.

### Стеки

Для каждого id: разрешённые размеры стека (1, 2, 3, 4) и шанс каждого размера в
процентах. Шансы нормализуются, если сумма не 100.

Разрешение конфликта «количество vs шансы»: **количество — закон, шансы — ориентир.**
Размеры тянутся по шансам, пока не наберётся заданное количество. Если очередной
вытянутый стек не влезает в остаток — он подрезается до остатка. Фактическая раскладка
стеков показывается в отчёте рядом с заказанной.

Пример: id 5, количество 10, шансы `1×:20%, 2×:50%, 3×:30%` → может выйти
`[2, 3, 2, 2, 1]`.

**Стеки одного символа никогда не ставятся вплотную.** Два соседних блока одного и того
же символа слиплись бы в один — заказанная раскладка размеров была бы уничтожена, и
любое правило дистанции стало бы возможно «выполнить», просто склеив всё в один блок.
Поэтому каждому блоку нужен разделитель.

Отсюда арифметическое ограничение, которое проверяется до генерации: если у символа `K`
блоков, а всех прочих блоков на ленте `M`, то разложить без слипания можно только при
`K ≤ M`. Символ, забивающий больше половины ленты мелкими стеками, разложить нельзя —
инструмент скажет об этом прямо и предложит увеличить размер его стеков.

### Дистанции

Правило — кортеж `(A, B, ≥N, наполнитель)`:

- `A`, `B` — класс (`low`/`middle`/`high`/`special`) или конкретный id
- `N` — минимальное количество символов между блоком A и блоком B
- `наполнитель` — опционально: класс, символами которого должен быть заполнен
  промежуток (например «между special и middle — минимум 2 символа, и это должны быть low»)

Примеры:

```
special ↔ special : ≥ 5 символов
special ↔ middle  : ≥ 2 символов, только low
id_10   ↔ id_10   : ≥ 8 символов
high    ↔ high    : ≥ 1 символ
```

Лента считается замкнутой в кольцо: расстояние между последней и первой позицией
измеряется через стык.

Точная семантика:

- дистанция измеряется между границами блоков (концом одного стека и началом другого),
  а не между их центрами
- правило проверяется только для **ближайших** пар: блок A и блок B, между которыми нет
  другого блока, подходящего под A или B. Далёкие пары не проверяются — иначе правило с
  наполнителем ломало бы ленту на ровном месте
- нарушение, если промежуток между парой короче N символов
- нарушение, если задан наполнитель и в промежутке меньше N символов этого класса.
  Промежуток длиннее N может содержать что угодно сверх этих N — требование «2 low между
  special и middle» означает «не меньше двух low», а не «весь промежуток из low»

## Движок генерации

Гибрид: жадная укладка с рестартами, при неудаче — локальный поиск. Каждый рил
генерируется независимо.

### Стадия 1 — сборка стеков

Из количеств и шансов собирается мультимножество блоков (см. «Стеки»).

Поскольку длина ленты равна сумме количеств, лента набита блоками плотно — свободных
позиций нет. Значит задача не «куда положить блок», а **в каком порядке расставить
блоки по кольцу**: расстояние между двумя блоками равно суммарному размеру блоков,
стоящих между ними.

### Стадия 2 — жадная укладка

Последовательность строится слева направо. На каждом шаге из оставшихся блоков берутся
кандидаты в случайном порядке; кандидат принимается, если новые образовавшиеся пары
«ближайших соседей» по каждому правилу не нарушены.

Важное свойство: когда блок дописан в конец, промежуток между ним и предыдущим
подходящим блоком уже полностью определён и дальше не меняется. Поэтому проверка
окончательна — задним числом ничего не ломается.

Среди допустимых кандидатов предпочтение отдаётся символу с наибольшим остатком
неразмещённых блоков — это само собой разносит частые «тугие» символы по ленте.

Когда все блоки размещены, кольцо замыкается: проверяется пара «последний подходящий
блок ↔ первый подходящий блок» через стык. Если не сошлось — рестарт с новым сидом, до
N попыток (по умолчанию 200, настраивается).

### Стадия 3 — локальный поиск (repair)

Если жадная не сошлась: блоки раскладываются случайной перестановкой, считается штраф —
сумма недостающих расстояний и недостающих наполнителей по всем нарушенным парам.
Дальше свопы пар блоков; своп принимается, если штраф не вырос. При застревании на
плато делается случайный своп. Останов при штрафе 0 либо по лимиту итераций.

### Диагностика невыполнимости

Перед генерацией считается нижняя граница нужной длины: для каждого правила
`(A, A, ≥N)` — `count_A_блоков × (размер_блока + N) ≤ длина ленты`; для правил между
разными классами — суммарная потребность в разделителях.

Если граница не сходится, генерация не запускается, а выдаётся конкретное объяснение:

> рил 3: 12 стеков special при `special↔special ≥5` требуют минимум 60 позиций-
> разделителей, а свободных 43. Ослабь дистанцию до 3 или убери 3 символа.

Если границы сходятся, но и жадная, и repair не уложились в лимиты — сообщается, какие
правила остались нарушены и на сколько.

### Сид

Каждая генерация записывает сид в отчёт. Сид можно задать вручную и получить в точности
ту же ленту. Сид сохраняется вместе с результатом в проект.

## Отчёт

### Раскладка картинками

Каждый рил — вертикальная колонка иконок, сбоку номера позиций. Стеки визуально
слипаются в блок (общая рамка). Окно 4 ряда можно двигать вверх/вниз, чтобы посмотреть,
как выглядит экран в конкретной позиции.

### Таблица состава

По каждому рилу: id, картинка, класс, количество, доля в процентах, фактическая
раскладка стеков против заказанной. Внизу — итог по всему рилсету.

### RTP

Считается точно, полным перебором через динамическое программирование — не симуляцией.

Расчёт линий: для каждой из 20 линий и каждого символа считается вероятность выигрышной
комбинации длины k (символ или вайлд на первых k рилах, и на рил k+1 — ни символ, ни
вайлд). Вайлд имеет собственные выплаты, поэтому для комбинации из одних вайлдов берётся
максимум из «выигрыш как вайлд» и «выигрыш как замещаемый символ». Вайлд не замещает
scat, bonus и hide.

Расчёт скаттера и бонуса: для каждой позиции рила считается число scat в окне из 4 рядов,
получается распределение по рилу; распределения по 5 рилам сворачиваются — получается
точная вероятность выпадения ровно k скаттеров. То же для бонуса.

Важное следствие: для конкретной линии видимый символ на барабане — это равномерный
выбор из ленты, а барабаны независимы. Поэтому RTP одной линии одинаков для всех 20
линий и не зависит от их рядов. Считаем один раз, умножаем на число линий; разбивки
«по линиям» в отчёте нет, она была бы бессмысленной.

Показывается:

- общий RTP линий; разбивка по символам, по длинам (3/4/5) — **точно**
- hit rate одной линии: 1 к X спинов — **точно**
- скаттер: частота 3+ (1 к X) и вклад `tb`-выплаты в RTP — **точно**
- бонус: частота триггера (порог настраивается, по умолчанию 3+), 1 к X — **точно**
- общий hit rate по всем 20 линиям — **оценка симуляцией**, помечена как оценка
- итог вида «линии 92.4% + скаттер 1.1% = 93.5%, фриспины не учтены»

Почему общий hit rate — оценка: 20 линий смотрят на одни и те же 5 барабанов и не
независимы. Точный перебор — это произведение длин лент (порядка 300⁵ ≈ 2.4·10¹²
комбинаций), что нереально. Считаем симуляцией на 200 000 спинов с фиксированным сидом
и показываем погрешность.

Ставка: 20 линий по 1, общая ставка 20. RTP = ожидаемый выигрыш / общая ставка.

## Архитектура

```
Reel Generator/
  run.py                 — точка входа: поднимает сервер, открывает браузер
  reelgen/
    model.py             — Symbol, Paytable, Payline, ReelStrip, ReelSet, GameConfig
    gameio.py            — парсинг и экспорт .py-формата игры
    images.py            — поиск картинок в папке, авто-маппинг на id
    rules.py             — RuleSet: состав, стеки, дистанции; проверка нарушений
    feasibility.py       — нижние границы и объяснение невыполнимости
    generate.py          — сборка стеков, жадная укладка, repair
    mathexact.py         — точный RTP линий, распределения scat/bonus
    stats.py             — состав и раскладка стеков по рилам
    project.py           — сохранение/загрузка projects/<имя>.json
    server.py            — локальный http-сервер, JSON API, отдача картинок
  web/
    index.html
    app.js
    style.css
  projects/              — сохранённые проекты
  tests/
```

Границы модулей: `rules.py` знает только, нарушено правило или нет, и ничего не знает
про то, как ленту строят. `generate.py` знает про укладку, но не про RTP.
`mathexact.py` принимает готовые ленты и пейтейбл, ничего не знает про правила.
`server.py` — тонкий слой, вся логика в модулях.

## Стек

Python 3, только стандартная библиотека — ничего ставить не нужно. Сервер на
`http.server`, фронт на чистом JS без сборки. Запуск: `python3 run.py`.

## Тесты

- `gameio`: круговой прогон — распарсить пример игры, экспортировать, сравнить с исходником
- `rules`: нарушения на кольцевых лентах, в том числе через стык; правило с наполнителем
  срабатывает на ближайшей паре и не срабатывает на далёкой
- `generate`: сгенерированная лента соответствует заказанным количествам точно;
  все правила дистанции соблюдены; один сид даёт одну и ту же ленту
- `feasibility`: заведомо невыполнимый набор правил ловится до генерации
- `mathexact`: RTP на игрушечной ленте, где ответ считается руками; распределение
  скаттеров суммируется в 1
